# ANÁLISIS Y PLAN DE IMPLEMENTACIÓN – SISTEMA DE TALLER MECÁNICO CON FACTURACIÓN ELECTRÓNICA SUNAT PERÚ

Actúa como un **arquitecto de software senior y especialista en desarrollo de sistemas empresariales, gestión de talleres mecánicos, Laravel, React, Inertia.js, MySQL y facturación electrónica SUNAT Perú**.

Tengo previsto desarrollar un sistema de gestión para un **taller mecánico**, utilizando mi propia API de facturación electrónica SUNAT Perú.

Antes de comenzar a programar, necesito que analices exhaustivamente la colección de Postman de mi API y, a partir de sus funcionalidades reales, elabores un análisis técnico y un plan de implementación detallado, organizado por módulos y fases.

**IMPORTANTE:** El sistema debe ser práctico, sencillo de utilizar y enfocado en las operaciones esenciales de un taller mecánico. No quiero desarrollar un ERP demasiado complejo ni agregar funcionalidades innecesarias.

Todos los productos deben contar con la posibilidad de tener una imagen asociada, pero el registro de esta imagen debe ser completamente opcional.

Implementar las siguientes funcionalidades:

- Permitir subir una imagen al registrar o editar un producto.

- Mostrar una vista previa antes de guardar.
- Permitir reemplazar o eliminar la imagen posteriormente.
- Aceptar formatos JPG, JPEG, PNG y WEBP.
- Validar el formato y tamaño máximo del archivo desde el backend.

Considerar un componente reutilizable para la carga, vista previa y gestión de imágenes de productos.

## 5. Integración con mi API SUNAT: regla obligatoria

Mi API propia ya gestiona internamente el procesamiento y envío de comprobantes electrónicos hacia SUNAT.

Por lo tanto, **NO debes implementar Jobs, Queues ni Workers de Laravel para enviar o procesar facturas, boletas, notas de crédito o notas de débito**.

Laravel debe consumir directamente mi API mediante solicitudes HTTP.

Flujo obligatorio:

1. Validar los datos de la venta.
2. Obtener la configuración fiscal de la empresa correspondiente.
3. Construir la solicitud según la estructura real de mi API.
4. Consumir directamente el endpoint correspondiente.
5. Recibir la respuesta.
6. Interpretar el resultado.
7. Guardar el identificador, estado y respuesta relevante.
8. Consultar posteriormente el estado si la API devuelve un documento pendiente o en proceso.
9. Habilitar la descarga de PDF, XML y CDR cuando estén disponibles.

Consideraciones importantes:

- No crear Jobs para el envío de comprobantes.
- No crear Workers para el envío de comprobantes.
- No duplicar el procesamiento que ya realiza mi API.
- No reenviar automáticamente un comprobante si ocurre un timeout sin comprobar primero si la API llegó a procesarlo.
- Evitar duplicidad de comprobantes.
- Registrar errores y respuestas para facilitar el diagnóstico.
- Si se necesita algún proceso programado para consultar estados pendientes, debe ser independiente del envío y no duplicar la lógica interna de la API.

El sistema debe permitir que cada empresa cliente configure sus propios datos fiscales desde su panel.

**IMPORTANTE:** Los clientes NO deben ingresar API Key ni API Secret de mi API SUNAT.

Mi API es un servicio interno que consume el backend Laravel.

Cada empresa debe registrar sus propios datos de emisor:

- RUC.
- Razón social.
- Nombre comercial.
- Dirección fiscal.
- Departamento.
- Provincia.
- Distrito.
- Ubigeo.
- Correo electrónico.
- Teléfono.
- Series de factura y boleta.
- Series de notas de crédito y débito, si corresponden.
- Establecimiento.
- Certificado digital.
- Contraseña del certificado.
- Ambiente u otros parámetros que realmente requiera la API.

El sistema debe permitir:

- Registrar y editar los datos fiscales.
- Subir el certificado digital.
- Reemplazar el certificado.
- Actualizar su contraseña.
- Validar la configuración.
- Probar la conexión o configuración, si la API lo permite.
- Mostrar el estado de la configuración.
- Mostrar la fecha de última actualización.

### Seguridad de credenciales

Las credenciales técnicas internas de mi API, como API Key y API Secret, si son necesarias, deben permanecer exclusivamente en el backend Laravel, mediante variables de entorno o un mecanismo seguro de gestión de secretos.

Nunca deben:

- Solicitarse al cliente.
- Mostrarse en React.
- Enviarse al navegador.
- Exponerse en respuestas HTTP.
- Registrarse en logs.

El backend debe combinar las credenciales internas del servicio con los datos fiscales y el certificado de la empresa correspondiente.

### Arquitectura multiempresa

Cada empresa debe tener su propia configuración fiscal, certificado, series y comprobantes.

Implementar aislamiento de datos mediante `company_id` o una estrategia equivalente.

Garantizar que:

- Una empresa no pueda visualizar información de otra.
- Una empresa no pueda modificar configuraciones ajenas.
- Cada comprobante utilice la configuración correcta.
- Los comprobantes históricos conserven sus datos originales aunque posteriormente cambie la configuración fiscal.

## 11. Registro inicial automático del Super Admin (Setup Wizard)

Este requisito es obligatorio y debe implementarse desde la primera fase del proyecto.

Cuando se instala el sistema por primera vez y todavía no existe ningún usuario con rol `super_admin`, **no debe mostrarse directamente el formulario de Login**.

En su lugar, el sistema debe iniciar automáticamente un proceso de configuración inicial para registrar al primer Super Admin.

### 11.1. Verificación inicial

Cuando una persona acceda al sistema:

1. Laravel debe verificar en el backend si existe un usuario con rol `super_admin`.
2. Si no existe, debe redirigir automáticamente al formulario de registro inicial.
3. Si ya existe, debe mostrar el Login normalmente.

La comprobación debe realizarse desde el backend y no depender de condiciones controladas por React.

### 11.2. Formulario de registro inicial

Crear una pantalla profesional y sencilla con los siguientes campos:

- Nombres.
- Apellidos.
- Correo electrónico.
- Contraseña.
- Confirmar contraseña.

Incluir:

- Validación de campos obligatorios.
- Validación de correo único.
- Contraseña segura.
- Confirmación de contraseña.
- Botón para mostrar u ocultar contraseña.
- Mensajes de validación claros.
- Diseño responsive.

### 11.3. Creación del primer Super Admin

Al enviar el formulario:

1. Laravel debe validar nuevamente todos los datos.
2. Crear el usuario inicial.
3. Asignarle automáticamente el rol `super_admin` desde el backend.
4. No permitir seleccionar ni modificar el rol desde el formulario.
5. Guardar la contraseña mediante el mecanismo seguro de hashing de Laravel.
6. Iniciar sesión automáticamente después del registro exitoso.
7. Redirigir al Dashboard o al siguiente paso de configuración inicial.

### 11.4. Bloqueo del registro inicial

Después de crear el primer Super Admin:

- El formulario de registro inicial debe quedar bloqueado.
- No debe permitirse volver a utilizarlo mediante una URL pública.
- No debe ser posible crear otro Super Admin manipulando solicitudes HTTP.
- La comprobación debe ejecutarse siempre en el backend.
- La creación debe ser segura frente a solicitudes simultáneas.

Utilizar transacciones y mecanismos de bloqueo o protección contra concurrencia para evitar que dos usuarios puedan registrarse como primer Super Admin al mismo tiempo.

### 11.5. Comportamiento después de la instalación

Una vez registrado el primer Super Admin:

- El acceso al sistema debe mostrar el Login.
- El Super Admin podrá iniciar sesión normalmente.
- Las rutas del Dashboard estarán protegidas.
- Los usuarios posteriores se crearán mediante mecanismos autorizados.
- El registro inicial no volverá a habilitarse mientras exista el Super Admin.

Si se instala nuevamente el sistema con una base de datos nueva y sin usuarios, el proceso de registro inicial debe ejecutarse automáticamente, sin necesidad de modificar el código.

### 11.6. Arquitectura recomendada

Organizar este proceso mediante:

- Middleware de verificación del estado de instalación.
- Controlador de registro inicial.
- Servicio para verificar el estado de instalación.
- Rutas específicas del Setup Wizard.
- Validaciones mediante Form Requests.
- Asignación de roles exclusivamente desde el backend.
- Transacción y protección contra concurrencia.

**Flujo esperado:**

Primera instalación:

Acceso al sistema → Verificación de Super Admin → No existe → Formulario de registro inicial → Crear Super Admin → Inicio de sesión automático → Dashboard.

Instalaciones posteriores:

Acceso al sistema → Verificación de Super Admin → Existe → Login → Autenticación → Dashboard según permisos.
